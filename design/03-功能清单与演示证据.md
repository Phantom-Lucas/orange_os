# 功能清单与演示证据

## 1. 证据原则

答辩中的“实现了”至少应对应两类证据：源码入口说明实现在哪里；运行结果或自动测试说明
功能确实经过外部观察。仅展示函数名、PPT 截图或代码行数不算完整证明。

## 2. 推荐现场命令

### 2.1 六步系统级展示

```text
about
ps
demo
cat demo-proof.txt
```

`demo` 的稳定检查点：

```text
ORANGE/64 GUIDED TOUR
PASS SYSTEM
PASS PROCESS + COW
PASS IPC
PASS THREADS
PASS FILESYSTEM
PASS FAULT ISOLATION
RESULT 6 passed 0 failed
```

PID、ticks、TID、页数与 fault 退出码是动态值，不要把某次截图中的数字背成固定结果。

### 2.2 Shell 组合能力（时间允许时）

```text
pwd
mkdir defense
echo orange64 > defense/result.txt
cat defense/result.txt
echo pipeline-ok | cat
sleep 20 &
ps
```

这组命令对应 cwd、目录、open/write、重定向、pipe、fork/exec、后台和进程观察。若演示镜像
已存在 `defense`，请提前删除或换名称，不要在台上临时排错。

### 2.3 故障隔离

```text
run fault.elf
help
```

判定标准不是“看到错误”，而是错误属于 Ring 3 子进程，随后 `help` 仍可执行，QEMU 没有
重启，内核没有 panic。

### 2.4 持久化

第一次演示运行 `demo` 后退出 QEMU，重新执行 `make fb-showcase`，再运行：

```text
cat demo-proof.txt
```

预期仍为 `ORANGE/64 showcase proof v1`。现场 10 分钟不必真的重启两次，可在 PPT 放自动
测试的双启动日志，现场只读取事先保留的 proof 文件。

## 3. 自动化证据位置

最终固定种子完整回归根目录：

```text
build/baseline/2026-08/final-current/
  20260821-015007-212744-20260821/
```

代表性视觉制品：

```text
framebuffer/core/1/framebuffer-1280x720.ppm
showcase/core/1/terminal-theme.ppm
```

`result.env` 中 `status=PASS` 是机器可读结论；`test.log` 记录交互检查点，`command.txt` 和
环境文件用于复现。提交前应从最终 tag 重跑并用新的路径替换这里，而不是只复制旧截图。

## 4. PPT 截图选择

只选两张：

1. framebuffer 终端全景：表现自研渲染、分辨率和 Shell。
2. guided tour 末尾：同时出现 `PASS FAULT ISOLATION`、`RESULT 6 passed 0 failed` 和 prompt。

截图旁用小字标注测试 case、seed 和 commit/tag。不要把一屏启动日志当作主要视觉材料，
也不要放无法在现场复现的装饰性效果。

## 5. 失败判定

- `INFRASTRUCTURE_ERROR`：如 QEMU monitor socket 权限，属于宿主测试基础设施问题，保留
  artifact 后修复环境，不能记录为 PASS。
- `TIMEOUT`：先检查是否有遗留 QEMU 抢占 CPU，再用相同 seed 重跑；低轮次通过不能替代
  压力门。
- `FAIL`：以最小 case 复现，记录实际/预期、日志和修改；不能只删除失败测试。
- 现场 `demo` 任一步 FAIL：停止扩展演示，保留画面并切到预先保存的测试证据，答辩后再查。
